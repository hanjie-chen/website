# Bilingual Site Phase 1 Design

Date: 2026-04-11
Status: Drafted for review

## Context

The website is evolving from a mixed-language personal site into a deliberately bilingual site. The long-term goal is full Chinese and English support across both site chrome and article content, but article-level bilingual publishing will be handled later.

Today the Flask app serves public pages without a language layer:

- templates mix Chinese and English copy directly
- `<html lang>` is fixed to `zh-CN`
- routes do not encode language in the URL
- no locale preference is stored across visits

This design covers Phase 1 only: establish the language mechanism and bilingual public page shell so the site can later support bilingual articles without route or UX rework.

## Goals

- Introduce explicit language-prefixed public routes under `/zh/...` and `/en/...`
- Add a top-bar language switcher on public pages
- Make `/` an automatic language entrypoint
- Persist the user's manual language choice with a lightweight cookie
- Localize public site chrome and fixed page copy for:
  - home
  - articles index and category pages
  - article detail page shell
  - about page
  - 404 page
- Keep the implementation lightweight and easy to extend in Flask

## Non-Goals

- No article-level bilingual pairing yet
- No geolocation-based language detection in Phase 1
- No migration to `Flask-Babel` or `gettext` in Phase 1
- No API localization contract changes in Phase 1 unless needed for route compatibility

## User Experience Summary

- Every public page exposes a visible Chinese/English switch control in the top bar
- The canonical public URLs are language-explicit:
  - `/zh/`
  - `/en/`
  - `/zh/articles`
  - `/en/articles`
  - `/zh/articles/category/<path>`
  - `/en/articles/category/<path>`
  - `/zh/articles/<id>`
  - `/en/articles/<id>`
  - `/zh/about`
  - `/en/about`
- `/` does not render content; it determines the preferred language and redirects with HTTP 302 to either `/zh/` or `/en/`
- Switching language updates the stored preference and moves the user to the corresponding route in the other language namespace

## Language Selection Rules

Phase 1 resolves the preferred language with this precedence:

1. `preferred_language` cookie
2. Browser `Accept-Language`
3. Default language: `zh`

Notes:

- Geolocation is intentionally excluded from Phase 1 to avoid avoidable misclassification
- The cookie exists only to store an explicit UI preference, for example `preferred_language=zh`
- The site should only accept supported language values (`zh`, `en`) and ignore invalid cookie values

## Route Design

Public routes move behind an explicit language prefix:

- `/<lang>/`
- `/<lang>/articles`
- `/<lang>/articles/category/<path:category_path>`
- `/<lang>/articles/<int:article_id>`
- `/<lang>/about`

Where `<lang>` is restricted to `zh` or `en`.

The root route `/` becomes a redirect-only entrypoint. It should:

- read the cookie if present
- otherwise evaluate `Accept-Language`
- fall back to `zh`
- redirect to the selected language home route

404 handling should remain language-aware:

- requests inside a language namespace should render a localized 404 page
- unmatched non-prefixed URLs should still land on the existing not-found handling, but public links generated by the app should always be language-prefixed

## Language Switch Behavior

The top-bar language switcher should:

- always be visible on public pages
- show the currently active language clearly
- switch between `/zh/...` and `/en/...` for the current page shape
- set or overwrite the `preferred_language` cookie when the user manually switches

Phase 1 page mapping rules:

- home maps to home
- about maps to about
- article index maps to article index
- category pages map to the same category path
- article detail pages map to the same article id

Because article bilingual pairing is out of scope for Phase 1, article detail switching changes the surrounding site language but still points at the same article record. The article body content itself remains whatever source content currently exists.

## Translation Architecture

Phase 1 uses a lightweight app-owned translation layer instead of `Flask-Babel`.

Recommended structure:

- define supported languages centrally in `app.py` or a small adjacent module
- store UI strings in a nested dictionary keyed by language and message key
- inject a translation function into Jinja, for example `t("nav.about")`
- inject route helpers into templates:
  - `current_lang`
  - `alternate_lang`
  - `switch_lang_url`

Why this approach is recommended now:

- low implementation cost for the current project size
- straightforward to reason about in Flask and Jinja
- avoids sprinkling template-level `if current_lang == ...` branches everywhere
- leaves room to migrate to a fuller i18n stack later if the UI copy surface grows substantially

## Page Content Scope

Phase 1 localizes:

- navigation labels
- footer copy
- 404 copy
- home page fixed copy
- about page fixed copy
- docs shell labels and helper text on article index pages
- article detail shell labels such as breadcrumbs, metadata labels, section navigation title, and TOC title

Phase 1 does not localize:

- article body HTML rendered from markdown
- article metadata fields authored in the source repository, such as article title or brief, unless those fields are already bilingual in source content

This means `/zh/articles/<id>` and `/en/articles/<id>` may initially render the same article title/body while the surrounding site shell changes language.

## Template and App Changes

Expected implementation shape:

- update route definitions to support language-prefixed public endpoints
- add language resolution helpers for root redirects and per-request page rendering
- update `base.html` so `<html lang>` is dynamic
- add a reusable top-bar language switch control
- replace hardcoded fixed UI copy in templates with translation lookups
- ensure generated internal links stay within the current language namespace

Special attention areas:

- breadcrumb links
- docs tree links
- article/category URLs generated from `url_for(...)`
- 404 rendering path

## Cookie Design

Cookie name:

- `preferred_language`

Cookie behavior:

- written only when the user explicitly switches language
- contains only a supported site language code
- used solely for language preference, not authentication or tracking

Phase 1 does not require more complex persistence than this cookie.

## SEO and Future Compatibility

Even though Phase 1 is not yet full bilingual article publishing, explicit language paths are still the correct foundation because they make future work possible:

- stable, shareable language-specific URLs
- later support for per-language canonical tags and `hreflang`
- later support for bilingual article pairing without route redesign
- cleaner caching semantics for HTML pages

Full SEO enhancements such as canonical strategy, `hreflang`, and multilingual sitemap generation should be specified when article-level bilingual support is designed.

## Testing Strategy

Phase 1 should add or update pytest coverage for:

- `/` redirecting according to:
  - valid cookie
  - `Accept-Language`
  - default fallback to `zh`
- localized route availability for:
  - home
  - articles index
  - category page
  - article detail
  - about
- language switch control rendering on public pages
- localized fixed UI text differences between `zh` and `en`
- language-aware 404 rendering
- regression coverage ensuring article and navigation routes still work with the new prefixed structure

README updates should accompany implementation because subsystem behavior changes at the route level.

## Risks and Trade-Offs

- A lightweight custom translation layer is simpler now, but it is less standardized than Babel tooling
- Phase 1 article pages may feel only partially bilingual because the shell changes before article bodies do
- Route migration must be handled carefully to avoid breaking internal links or tests

These trade-offs are acceptable because the chosen design intentionally optimizes for a clean foundation before article-level bilingual content arrives.

## Recommended Follow-Up Plan

Implementation planning should treat Phase 1 as a focused routing and template localization project:

1. Introduce language-aware routing and root redirect behavior
2. Add translation helpers and dynamic template context
3. Localize shared layout, home, about, article index, article detail shell, and 404 page
4. Add/update tests
5. Update `web-app/README.md` and root `Readme.md` if route behavior changes are documented there

## Open Items Deferred to Phase 2

- Whether bilingual metadata lives in frontmatter, separate files, or a higher-level pairing manifest
- How article switching behaves when only one language version exists
